Cours 3 · Bases numériques

Lire et modifier le logiciel du robot sans être programmeur

Faire marcher le canard ne demande pas d'écrire du code, mais de lancer les bons programmes, de régler un fichier sans le casser et de lire un message d'erreur. Ce cours vous en donne les moyens.

Durée : 50 min Niveau : débutant Prérequis : cours 2 Rôles : référent électronique et code, membres du banc

À la fin de ce cours, vous saurez

  • Lancer un programme avec ses options, depuis le bon dossier.
  • Préparer l'environnement de travail avant de lancer quoi que ce soit.
  • Vous repérer dans le dossier du logiciel embarqué.
  • Modifier le fichier de réglages du robot sans le casser.
  • Dire ce que fait chaque programme de calibration et de marche, et quels réglages ne jamais toucher.
  • Lire un message d'erreur en partant de la dernière ligne.

1. Python, un script, une commande

Python est un langage de programmation réputé lisible : tout le logiciel du canard est écrit avec. Un script est un fichier Python (nom terminé par .py) qu'on lance en une commande pour faire une tâche précise. Image mentale : une recette, que l'ordinateur suit ligne par ligne.

python nom.py --option valeur
python configure_motor.py --id 10

Une option commence par deux tirets et peut attendre une valeur : ici, --id 10 donne le numéro à attribuer au servo. Une option obligatoire oubliée provoque un message qui la nomme. python nom.py --help affiche la liste des options, pour les scripts qui en ont.

Le dossier courant compte

Certains scripts lisent ou écrivent des fichiers « ici », c'est-à-dire dans le dossier où vous êtes au moment de lancer. Sur notre robot, on lance toujours depuis ~/Open_Duck_Mini_Runtime/scripts.

Exemple sur notre canard

Le script de marche lit ./polynomial_coefficients.pkl, rangé dans scripts/, et la calibration de l'IMU (la centrale inertielle, l'oreille interne du robot) est écrite dans le dossier courant. Lancés depuis un autre dossier, ils ne retrouvent pas leurs fichiers.

2. L'environnement virtuel et pip

Le runtime, le programme qui tourne sur le Pi pendant la marche, a besoin de bibliothèques à des versions exactes : onnxruntime 1.18.1, numpy 1.26.4, rustypot 0.1.0. Un environnement virtuel (en anglais virtual environment, abrégé venv) est un dossier isolé qui contient une version de Python et ces bibliothèques, sans mélange avec le reste du système. Image mentale : la caisse à outils du projet, rangée à part de l'atelier commun.

L'activer

source chemin/du/venv/bin/activate
source ~/.virtualenvs/open-duck-mini-runtime/bin/activate
workon open-duck-mini-runtime       # raccourci équivalent

L'invite affiche alors le nom de l'environnement entre parenthèses. Il faut l'activer à chaque nouvelle connexion ; l'image prête du canard essaie de le faire automatiquement à la connexion SSH. deactivate en sort.

pip install -e .

pip est l'installateur de bibliothèques Python. Dans le dossier du dépôt, pip install -e . se lit ainsi : . = « ce dossier-ci » ; -e = « éditable » : le runtime est installé en lien direct avec le dossier, donc une modification d'un de ses fichiers est prise en compte sans réinstaller. pip lit dans setup.cfg la liste des bibliothèques à installer, avec leurs versions.

Exemple sur notre canard

Sur l'image prête, l'environnement s'appelle open-duck-mini-runtime. Si l'invite ne l'affiche pas après la connexion, on tape workon open-duck-mini-runtime avant tout script.

Erreur classique. Lancer pip install ou un script sans avoir activé l'environnement. Sous Bookworm, pip refuse avec externally-managed-environment ; un script, lui, ne trouve pas ses bibliothèques. Premier réflexe devant une erreur : l'environnement est-il activé ?

4. Lire et modifier un fichier JSON

Le JSON est un format texte de réglages : des paires "clé": valeur séparées par des virgules, entre accolades. Une valeur peut être un nombre, true ou false, un texte entre guillemets, ou un groupe entre accolades. Voici le modèle fourni, avec start_paused passé à true :

{
    "start_paused": true,
    "imu_upside_down": false,
    "phase_frequency_factor_offset": 0.0,
    "expression_features": {
        "eyes": false,
        "projector": false,
        "antennas": false,
        "speaker": false,
        "microphone": false,
        "camera": false
    },
    "joints_offsets": {
        "left_hip_yaw": 0.0,
        "left_hip_roll": 0.0,
        "left_hip_pitch": 0.0,
        "left_knee": 0.0,
        "left_ankle": 0.0,
        "neck_pitch": 0.0,
        "head_pitch": 0.0,
        "head_yaw": 0.0,
        "head_roll": 0.00,
        "right_hip_yaw": 0.0,
        "right_hip_roll": 0.0,
        "right_hip_pitch": 0.0,
        "right_knee": 0.0,
        "right_ankle": 0.0
    }
}

start_paused : à true, la marche attend l'appui sur A. imu_upside_down : capteur monté à l'envers ou non. phase_frequency_factor_offset : ajuste la cadence des pas. joints_offsets : les 14 décalages de zéro, mesurés sur notre robot.

Cinq pièges, et ce que Python répond

Pour vérifier un fichier après chaque modification : python -m json.tool ~/duck_config.json. S'il est valide, il s'affiche ; sinon, un de ces messages. La ligne indiquée est l'endroit où Python s'est arrêté : la faute est là ou juste avant.

Exemple sur notre canard

Le message « line 28 column 5 » désigne l'accolade qui ferme joints_offsets. La vraie faute est à la ligne 27 : la virgule après "right_ankle": 0.0.

5. Tour guidé des scripts

Tous se lancent depuis scripts/, environnement activé, robot sur support ou banc, mains hors des articulations.

configure_motor.py --id N

Un servo neuf à la fois sur le bus. Le script cherche l'ID d'usine 1, écrit le gain P (la raideur du servo) = 32, I = 0, D = 0, accélération 0, mode 0, donne le nouvel ID, puis envoie le servo en position 0 : on monte alors le palonnier aligné. Seul réglage à choisir : le numéro (10 à 14, 20 à 24, 30 à 33). Option --port si la carte n'est pas sur /dev/ttyACM0.

check_motors.py

Sans option. Il interroge les 14 servos, liste ceux qui ne répondent pas et demande s'il faut continuer (y/n). Puis, servo par servo, il demande « Test this motor? » et le fait bouger de 0,1 rad avant de le ramener.

check_voltage.py

Affiche la tension vue par chaque servo de la liste écrite dans le script. Utile pour traquer une chute de tension sous charge, cause d'erreurs CRC (issue #49).

find_soft_offsets.py

Pour chaque articulation, il coupe le couple, vous la placez à zéro à la main, il mesure l'offset (décalage de zéro). À la fin, il affiche les valeurs : on les recopie dans joints_offsets de ~/duck_config.json. L'issue #32 rapporte une tête et une jambe qui ont bougé ensemble et cassé des pièces : robot sur support, une articulation à la fois.

calibrate_imu.py

Attend que l'IMU soit entièrement calibrée, puis écrit imu_calib_data.pkl dans le dossier courant. D'où la règle : on le lance depuis le dossier où l'on lancera la marche.

turn_on.py

Met les servos sous tension en douceur : gain P = 2, amène le robot en posture initiale, puis remonte le gain.

v2_rl_walk_mujoco.py --onnx_model_path BEST_WALK_ONNX_2.onnx

La marche. Elle exécute la politique (le réseau qui décide des mouvements) avec start_paused lu dans la configuration. Ses options par défaut ne se touchent pas :

  • -p 30 : gain P des jambes (8 pour la tête) ;
  • -c 50 : fréquence de contrôle de 50 Hz, un calcul toutes les 20 ms ;
  • -a 0.25 : action_scale, qui réduit les sorties du réseau ;
  • --cutoff_frequency : filtre désactivé par défaut. On ne l'active pas.

Ce qu'on peut ajuster sans danger : phase_frequency_factor_offset dans la configuration, ou la croix de la manette (cadence ±0,05).

Exemple sur notre canard

Phase 2, sur le banc : python configure_motor.py --id 10 avec un seul servo branché, on le débranche, --id 11 avec le second, puis on les rebranche ensemble et python check_motors.py.

Pourquoi c'est comme ça. La politique a appris en simulation avec exactement P = 30, 50 Hz, action_scale 0,25 et sans filtre. Changer une de ces valeurs, c'est lui présenter un robot qu'elle n'a jamais vu : elle le fera tomber.
Erreur classique. Monter P « pour que le robot soit plus ferme ». La marche apprise ne correspond plus au robot.

6. Lire une erreur Python

Quand un script plante, Python affiche un Traceback (trace de pile) : le chemin suivi dans le code jusqu'à l'erreur, du plus général en haut au plus précis en bas. On lit la dernière ligne d'abord : le type d'erreur, deux-points, l'explication. On remonte ensuite seulement si besoin.

Traceback (most recent call last):
  File "/home/bdxv2/Open_Duck_Mini_Runtime/scripts/check_motors.py", line 6, in <module>
    from mini_bdx_runtime.rustypot_position_hwi import HWI
ModuleNotFoundError: No module named 'mini_bdx_runtime'
Exemple sur notre canard

Ce Traceback est celui de check_motors.py lancé sans environnement activé. Dernière ligne : la bibliothèque du runtime est introuvable. Ligne du dessus : c'est la ligne 6 du script, celle qui l'importe. Remède : workon open-duck-mini-runtime.

Dernière ligneCe que ça veut direQue faire
ModuleNotFoundError: No module named '…'Une bibliothèque est introuvable.Activer l'environnement ; sinon pip install -e . dans le dépôt.
FileNotFoundError: [Errno 2] No such file or directory: '…'Un fichier n'est pas là où le script le cherche.pwd : êtes-vous dans scripts/ ? Le nom est-il exact ?
PermissionError: [Errno 13] Permission denied: '/dev/ttyACM0'L'utilisateur n'a pas le droit d'ouvrir le port des servos.L'ajouter au groupe dialout (sudo usermod -aG dialout $USER), se reconnecter.
SerialException: [Errno 2] could not open port /dev/ttyACM0Le port n'existe pas ou est occupé.Câble USB, ls /dev/ttyACM*, service de marche arrêté ?

Selon la bibliothèque utilisée par le script, le même problème de port peut apparaître sous un autre nom d'erreur, ou à l'intérieur d'une SerialException. Le mot qui compte est le port, /dev/ttyACM0.

Deux messages ne sont pas des plantages Python mais des lignes de log à reconnaître : « Parsing error in set_kps() » (servos aux firmwares différents, issue #26) et les erreurs CRC (message abîmé sur le bus).

Erreur classique. Lire « Traceback » en haut, prendre peur, et envoyer une photo floue de l'écran sur Signal. On ouvre une issue avec la commande lancée, les dernières lignes copiées en texte, et ce qu'on avait fait juste avant.

7. Les 5 lignes de Python à comprendre

vitesse_max = 0.15                    # une variable : un nom, une valeur
jambe_droite = [10, 11, 12, 13, 14]   # une liste : des valeurs dans l'ordre
reglages = {"start_paused": True}     # un dictionnaire : des paires clé: valeur
for id_servo in jambe_droite:         # une boucle : pour chaque élément…
    if id_servo == 13:                # une condition : seulement si c'est vrai
        print("genou droit")
  • Variable : = range une valeur sous un nom. Ici la vitesse avant maximale de la manette, 0,15 m/s, écrite avec un point.
  • Liste : entre crochets, dans l'ordre. Ici les ID de la jambe droite.
  • Dictionnaire : entre accolades, comme le JSON. Attention : Python écrit True avec une majuscule, le JSON true sans.
  • Boucle for : répète le bloc décalé en dessous pour chaque élément. Le décalage (4 espaces) délimite le bloc : il n'est pas décoratif.
  • if : n'exécute le bloc que si la condition est vraie. == compare, = range.

Tout ce qui suit # est un commentaire, ignoré par Python.

Exemple sur notre canard

Dans check_voltage.py, vous reconnaîtrez un dictionnaire joints qui associe chaque articulation à son ID, puis une boucle for qui affiche la tension de chacune. Sur le banc, avec deux servos seulement, on en fera une copie dans notre dossier biscalab/ qui ne garde que 10 et 11.

8. « Policy control budget exceeded »

La marche doit faire un tour complet (lire les capteurs, calculer, envoyer les consignes) toutes les 20 ms. Quand un tour dure plus, le script affiche « Policy control budget exceeded by » suivi du dépassement en secondes. Le robot réagit alors en retard sur ce que la politique attend.

On note quand le message apparaît (au lancement, en marche, en continu), on vérifie qu'aucun autre programme lourd ne tourne (top, q pour quitter), et on ouvre une issue avec le log.

9. Noter ce qu'on a changé

Un réglage qui n'est écrit nulle part sera perdu au prochain reflashage. Deux traces, toujours :

  • le journal de bord de la séance : ce qu'on a changé, pourquoi, ce qu'on a observé ;
  • un commit dans notre dépôt du runtime : biscalab/duck_config.json, avec la date dans le message.

Pour rapatrier le fichier sur le PC, dans PowerShell : scp bdxv2@bdxv2.local:~/duck_config.json . (le point final = « ici »). On le copie dans biscalab/ du clone, puis GitHub Desktop : résumé « Offsets après calibration du … », Commit, Push. Ce qui a marché à l'installation va dans biscalab/INSTALL-biscalab.md. On ne modifie jamais un fichier de l'amont ; une correction utile à tous est proposée à Antoine Pirrone par pull request (voir cours 1).

Exercice pratique au FabLab

Matériel : le banc servo (Pi avec l'image prête, carte Waveshare, servos 10 et 11 configurés, alimentation de laboratoire réglée à 7,4 V et limitée en courant), un PC avec PowerShell. Durée : environ 25 min.

  1. Se placer : ssh bdxv2@bdxv2.local, vérifier que l'environnement est actif, cd ~/Open_Duck_Mini_Runtime/scripts.
  2. Sauvegarder : cp ~/duck_config.json ~/duck_config.json.bak.
  3. Modifier : nano ~/duck_config.json, passer start_paused à la valeur inverse, enregistrer. Vérifier avec python -m json.tool ~/duck_config.json.
  4. Se tromper exprès : écrire True avec une majuscule, revérifier, lire le message, corriger. Remettre enfin start_paused à true.
  5. Tester : python check_motors.py. Les 12 servos absents sont signalés, avec beaucoup de messages d'erreur : c'est normal sur le banc. Répondre y, puis Entrée. Tester 10 et 11 : chacun bouge de 0,1 rad et revient.
  6. Provoquer une erreur : débrancher le câble USB de la Waveshare, relancer. Le script affiche « Error connecting to hardware », un Traceback, puis « Check that the robot is powered on and USB connection is correct ». Lire la dernière ligne du Traceback.
  7. Réparer : rebrancher, ls /dev/ttyACM*, relancer : tout répond.

Résultat attendu : un fichier de réglages valide avec start_paused à true, deux servos testés, et dans le journal de séance le message d'erreur copié et sa cause.

Auto-contrôle

ModuleNotFoundError: No module named 'onnxruntime' : que vérifier en premier ?

Que l'environnement virtuel est activé. S'il l'est, réinstaller avec pip install -e . dans le dépôt.

Qu'est-ce qui ne va pas dans "start_paused": True, placé juste avant l'accolade finale ?

Deux fautes : True doit s'écrire true en JSON, et la virgule avant l'accolade est interdite.

Pourquoi ne pas lancer la marche avec -p 40 pour un robot plus ferme ?

La politique a été entraînée avec P = 30. Un autre gain lui présente un robot inconnu : elle le fait tomber.

Depuis quel dossier lance-t-on la marche, et pourquoi ?

Depuis scripts/ : le script y lit polynomial_coefficients.pkl, et la calibration de l'IMU y a été écrite.

Que signifie « Policy control budget exceeded » ?

Un tour de boucle a dépassé 20 ms : le robot réagit en retard. On note les circonstances et on ouvre une issue avec le log.

À retenir

  • python nom.py --option valeur, depuis scripts/, environnement activé.
  • Première cause d'erreur : l'environnement virtuel n'est pas activé.
  • pip install -e . installe le runtime en lien direct avec son dossier.
  • JSON : guillemets droits, true/false en minuscules, point décimal, pas de virgule finale. Vérifier avec python -m json.tool.
  • On ne touche pas à P = 30, 50 Hz, action_scale 0,25, ni au filtre.
  • Un Traceback se lit par la dernière ligne.
  • Chaque changement : une ligne au journal, un commit de duck_config.json.
