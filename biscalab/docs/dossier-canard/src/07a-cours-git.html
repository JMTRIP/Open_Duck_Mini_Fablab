Cours 1 · Bases numériques

Git et GitHub, en partant de zéro

Tout ce que nous produisons pour le canard (pièces, réglages, fiches de test, journal) vit dans un dossier partagé en ligne. Ce cours vous apprend à y lire, à y écrire et à y travailler à plusieurs sans écraser le travail d'un autre.

Durée : 45 min Niveau : débutant Prérequis : aucun Rôles : tout le monde

À la fin de ce cours, vous saurez

  • Expliquer pourquoi on garde un historique au lieu de renommer ses fichiers.
  • Distinguer les trois étages : le dépôt d'Antoine, le dépôt du club, votre PC.
  • Faire les 5 gestes de base avec un logiciel à boutons, sans aide.
  • Enregistrer une séance ou une pièce depuis la page, et reconnaître ce que GitHub affiche alors.
  • Ouvrir une tâche claire et la suivre sur le tableau de l'équipe.
  • Éviter, puis résoudre, une collision entre deux modifications.
  • Respecter la licence du projet d'origine.

1. Pourquoi garder un historique

Imaginez un dossier partagé contenant piece.stl, piece_v2.stl, piece_v3_final.stl et piece_v3_final_vraiment.stl. Laquelle a été imprimée la semaine dernière ? Qui a élargi le trou, et pourquoi ? Personne ne sait. Un mois plus tard, on réimprime la mauvaise.

Un nom de fichier ne peut pas raconter une histoire. Git est un logiciel qui le fait à sa place : il enregistre l'historique complet d'un dossier, avec pour chaque changement qui l'a fait, quand, et pourquoi. On peut revenir en arrière, comparer deux versions, travailler à plusieurs sans s'écraser.

L'image à garder : le cahier de laboratoire

Un bon cahier de laboratoire a des pages datées et signées. On n'arrache jamais une page : on écrit une nouvelle entrée qui corrige la précédente. Git tient ce cahier pour chaque fichier du projet. Le fichier garde son nom ; le cahier se souvient de ses versions.

Exemple sur notre canard

Les 36 fichiers STL (maillages de triangles qu'on imprime) du projet d'origine gardent leur nom, par exemple foot_bottom_tpu.stl. Si nous retouchons une pièce, sa copie va dans biscalab/print/stl/ sous le même nom, et la révision est notée dans le champ rev du registre des pièces et dans CHANGELOG.md.

Erreur classique. Ajouter _v2_final au nom pour marquer une version. Cela sème le doute et casse les projets d'impression, qui gardent le nom du fichier source pour le recharger.

2. Trois mots : dépôt, commit, branche

Le dépôt, c'est le cahier

Un dépôt (en anglais repository, ou « repo ») est un dossier ordinaire dont Git garde tout l'historique. Le dossier et son cahier voyagent ensemble.

Le commit, c'est une photo datée

Un commit est un enregistrement dans l'historique : Git photographie l'état des fichiers choisis et y colle une légende (le message), votre nom et la date. On peut revenir à n'importe quelle photo. Pour un fichier texte, Git montre aussi les lignes exactes qui ont changé.

La branche, c'est un chemin parallèle

Une branche est une ligne d'historique qui avance à côté de la ligne principale. Dans la plupart des projets, la ligne principale s'appelle main ; dans le nôtre, elle s'appelle v2, nom hérité du projet d'Antoine (la version 2 du canard). On essaie une idée dans une branche sans déranger personne. Si elle est bonne, on fusionne (en anglais merge) la branche dans v2 ; sinon on l'abandonne.

Exemple sur notre canard

Un membre dessine un gabarit pour aligner les palonniers des servos. Il travaille dans la branche prenom/gabarit-zero pendant deux semaines, puis propose de la fusionner. Pendant ce temps, les autres avancent sur v2 sans voir son travail à moitié fini.

Pourquoi un message à chaque commit. Dans six mois, la photo dira quoi ; seul le message dira pourquoi.

3. Trois étages : le dépôt d'Antoine, le dépôt du club, votre PC

Git tourne sur votre PC. GitHub est un site web qui garde des dépôts en ligne et ajoute des outils d'équipe : tâches, tableaux, relecture. Pour le canard, il n'y a que trois étages à retenir.

Étage 1 : le dépôt d'Antoine, l'original

apirrone/Open_Duck_Mini est le dépôt d'Antoine Pirrone, qui a conçu le canard et continue à l'améliorer. On n'y écrit jamais. On s'en sert seulement pour récupérer ses corrections, une fois par mois (section 10). On l'appelle aussi l'amont.

Étage 2 : le dépôt du club, le seul où l'on travaille

Jean-Marie a copié une fois pour toutes le dépôt d'Antoine sur son compte GitHub : JMTRIP/Open_Duck_Mini_Fablab. C'est le dossier commun de l'équipe, en ligne. Tout le monde travaille dedans ; personne n'a besoin d'en créer un autre. GitHub appelle ce genre de copie un fork : vous verrez le mot sur la page (« forked from apirrone/Open_Duck_Mini »), mais vous n'aurez jamais à en faire un.

Pour y écrire, il faut y être invité : Jean-Marie vous ajoute comme collaborateur (Settings → Collaborators → Add people). Vous recevez un e-mail « invited you to collaborate » : cliquer Accept invitation.

Étage 3 : votre PC, votre copie de travail

Chacun télécharge le dépôt du club sur son PC, une seule fois, avec GitHub Desktop (section 4). GitHub appelle cette copie un clone. C'est là que vous modifiez les fichiers. Ensuite, deux boutons suffisent :

  • Pull (récupérer), en arrivant : le travail des autres descend du dépôt du club vers votre PC ;
  • Push (envoyer), en partant : votre travail monte de votre PC vers le dépôt du club.

Dans le logiciel, le dépôt du club s'appelle origin : « Pull origin » veut dire « récupérer depuis le dépôt du club ».

Exemple sur notre canard

Dans le dépôt du club, tout ce qui vient d'Antoine reste tel quel ; tout ce qui est à nous va dans le dossier biscalab/. Un second dépôt du club, copie de Open_Duck_Mini_Runtime (le code qui tourne sur le robot), sera créé de la même façon par Jean-Marie.

Erreur classique. Au premier téléchargement, GitHub Desktop demande « How are you planning to use this fork? » (comment comptez-vous utiliser cette copie ?). Répondre For my own purposes (pour mon propre usage). Sinon, vos propositions partent chez Antoine Pirrone au lieu de rester au club.
Et l'« organisation biscalab » ? Plus tard, Jean-Marie pourra transférer le dépôt du club dans une organisation GitHub gratuite au nom du FabLab, pour avoir deux administrateurs au lieu d'un. Pour vous, rien ne changera : même contenu, et l'ancienne adresse redirige vers la nouvelle.

4. Les 5 gestes avec GitHub Desktop

GitHub Desktop est une application gratuite qui fait les gestes de Git avec des boutons. Elle n'existe qu'en anglais : voici chaque bouton, traduit. En haut, Current branch (branche courante) et un bouton de synchronisation dont le texte change selon la situation ; à gauche, l'onglet Changes (modifications).

  1. Télécharger (cloner), une fois par PC. Sur la page GitHub du dépôt du club, bouton vert Code → Open with GitHub Desktop. Ou, dans GitHub Desktop, menu File → Clone repository (Fichier → Cloner un dépôt), onglet GitHub.com, choisir JMTRIP/Open_Duck_Mini_Fablab. Indiquer le dossier dans Local path, cliquer Clone, puis répondre For my own purposes.
  2. Récupérer, en arrivant. Fetch origin regarde s'il y a du neuf sur GitHub sans rien changer chez vous. S'il y en a, le bouton devient Pull origin : cliquer. C'est le pull : le travail des autres arrive sur votre PC.
  3. Commiter, après chaque étape cohérente. Dans Changes, cocher les fichiers qui vont ensemble. En bas à gauche, écrire le résumé dans Summary (obligatoire), le pourquoi dans Description si utile, puis cliquer Commit to v2.
  4. Pousser, en partant. Le bouton devient Push origin : cliquer. C'est le push : vos commits partent sur GitHub. Avant, ils n'existent que sur votre PC.
  5. Brancher et proposer. Current branch → New branch, nom prenom/sujet, Create branch. Commiter normalement, cliquer Publish branch, puis Create Pull Request : le navigateur s'ouvre sur GitHub. Vérifier en haut que la cible est JMTRIP/Open_Duck_Mini_Fablab, branche v2, et non le dépôt d'Antoine, puis valider.

Une pull request (demande de fusion) propose de fusionner une branche dans une autre : un référent relit les modifications ligne par ligne, commente, puis accepte avec Merge.

Exemple sur notre canard

En arrivant : Fetch origin, Pull origin. On prépare dans PrusaSlicer le plateau des pieds et on l'enregistre dans biscalab/print/3mf/plateau-pieds.3mf. En partant : cocher ce fichier, résumé « Ajoute plateau des pieds », Commit to v2, Push origin. Le soir, Jean-Marie voit le plateau depuis chez lui. Les pièces sorties de l'imprimante et la séance, elles, s'enregistrent depuis la page, sans GitHub Desktop (section 9) ; le Pull suivant les ramène sur le PC.

Erreur classique. Sans pull en arrivant, on travaille sur une version périmée et on prépare une collision avec le travail des autres (section 7). Sans push en partant, on obtient le fameux « je croyais que tu l'avais fait ». La règle : Pull en arrivant, Push en partant.

5. Issues, étiquettes, jalons et tableau

Une issue est une fiche GitHub pour une tâche, un problème ou une question : titre, description, responsable (Assignees), étiquettes (Labels) et l'étape du projet à laquelle elle appartient (Milestone, voir plus bas). Chaque issue a un numéro : écrire #12 dans un commentaire ou un commit crée un lien vers l'issue 12. Quand c'est fait, on la ferme avec une preuve (photo, mesure ou commit). Quatre modèles s'ouvrent comme des formulaires : Tâche, Problème, Achat, Test.

Étiquettes et jalons

Une étiquette (en anglais label) est un mot coloré qui sert à trier : phase-0 à phase-6 ; impression, laser, cao, elec, code ; achat, securite, bloque, aide-bienvenue. Un jalon (en anglais milestone) regroupe les issues d'une étape, avec une date et une barre de progression. Nous en avons un par phase.

Le tableau Projects

Chaque issue y devient une carte, rangée en colonnes À faire, En cours, Fait. Quand l'état change, on fait glisser la carte. Le point hebdomadaire se fait devant ce tableau.

Exemple sur notre canard

Issue « Configurer les servos 10 et 11 sur le banc » : étiquettes phase-2, elec, code ; jalon Phase 2 ; responsable le référent électronique et code ; colonne En cours. Quand les deux servos répondent, il la ferme en collant la sortie du script.

6. Bien écrire : commits et titres d'issues

Un message de commit commence par un verbe au présent suivi de l'objet : « Ajoute gabarit zéro servo », « Corrige kerf plaque banc ». Une ligne courte ; le pourquoi en description si besoin. Un commit = une idée. Un titre d'issue dit l'action, l'objet et la précision ; pour un problème, le symptôme observé, pas la cause supposée.

À éviterÀ préférerPourquoi
« modif »« Ajoute plateau 3MF des pieds »On sait ce qui a changé sans ouvrir le fichier.
Issue « Laser »« Mesurer le kerf du contreplaqué 3 mm sur la P2S »N'importe qui peut la prendre.
Issue « Servo 11 mort »« Le servo 11 ne répond pas à check_motors »Le symptôme est un fait ; la cause reste à trouver.
Erreur classique. Un commit fourre-tout de fin de journée, message « update » : si une modification pose problème, impossible de l'isoler.

7. Conflits, fichiers binaires et taille

Le conflit

Un conflit survient quand deux personnes ont modifié la même ligne du même fichier. Git ne choisit pas : il écrit les deux versions entre des marqueurs.

<<<<<<< HEAD
Prochaine séance : mardi, impression des pieds
=======
Prochaine séance : jeudi, découpe du banc
>>>>>>> origin/v2

En haut votre version, en bas celle de GitHub. On discute, on garde le bon texte, on supprime les lignes de marqueurs, on enregistre. GitHub Desktop affiche « No conflicts remaining » (plus de conflit) : cliquer Continue merge (continuer la fusion), puis Push origin.

Les fichiers binaires ne se fusionnent pas

Un fichier binaire est une suite d'octets que seul son logiciel sait lire. Nos fichiers de pièces le sont : le STL, le FCStd (fichier FreeCAD, en réalité une archive zip) et le 3MF (projet d'impression avec position sur le plateau et réglages). Git ne sait pas mélanger deux versions : il faudrait en jeter une, donc le travail de quelqu'un.

D'où la règle « un éditeur par fichier » : celui qui modifie une pièce s'assigne l'issue correspondante, et personne d'autre n'enregistre ce fichier tant qu'elle lui est assignée. C'est un verrou humain.

La taille

GitHub avertit au-delà de 50 Mio par fichier et refuse au-delà de 100 Mio (un Mio, ou mébioctet, vaut un peu plus qu'un mégaoctet). Nos STL sont petits ; les photos en pleine résolution et les vidéos vont sur le Nextcloud du BiscaLab.

Exemple sur notre canard

Deux membres veulent retoucher le même gabarit FreeCAD. Le premier s'est assigné l'issue ; le second le voit sur le tableau et attend, ou travaille en binôme avec lui.

Erreur classique. Ouvrir un FCStd « juste pour regarder », bouger une cote, enregistrer par réflexe. Sans l'issue assignée, on ferme sans enregistrer.

Le suivi n'utilise pas de CSV : tout, rôles compris, est fait de petits fichiers Markdown créés depuis la page (section 9). Le CSV sert ailleurs : la BOM exportée d'un tableur, une liste de mesures relevées en série, qu'on dépose dans biscalab/ et que GitHub affiche en tableau.

Erreur classique. Une virgule dans une valeur : « Référent laser, impression » se coupe en deux colonnes. Mettre la valeur entre guillemets droits. Un tableur réglé en français enregistre souvent avec des points-virgules : vérifier sur GitHub que le tableau s'affiche bien avant de s'en servir.

9. Enregistrer depuis la page

Pour le suivi du projet (une séance, une pièce imprimée, un achat, une mesure, une décision, une fiche de test, une case cochée), GitHub Desktop est inutile. Ce dossier est aussi le tableau de bord du projet : chaque bouton « Enregistrer » (ou « Nouvelle séance », « Nouvel achat »…) déplie un petit formulaire dans la page ; sur une rubrique encore vide, il est déjà là. La page en tire un enregistrement, un fichier Markdown de quelques lignes, puis ouvre GitHub avec ce fichier déjà écrit. Il ne reste qu'à valider. Le principe est détaillé au cours 4 ; voici ce que l'on voit à l'écran.

Ce que GitHub affiche

  1. Préparer. Remplir le formulaire, cliquer Préparer l'enregistrement : la page montre le chemin du fichier et son texte. Cliquer Enregistrer sur GitHub : GitHub s'ouvre dans un nouvel onglet, connecté à votre compte.
  2. Vérifier. GitHub affiche sa page de création de fichier (l'onglet s'intitule « New File », nouveau fichier). Tout est déjà rempli : en haut, le chemin Open_Duck_Mini_Fablab / biscalab / journal /, une case avec le nom du fichier (par exemple 2026-10-14.md) et la mention « in v2 » (dans la branche v2) ; dessous, le contenu. Il commence par l'en-tête, quelques lignes clé : valeur entre deux lignes ---, puis vient le texte. On relit ; on peut corriger une faute.
  3. Valider. Cliquer le bouton vert Commit changes… (valider les modifications), en haut à droite.
  4. Confirmer. Une fenêtre s'ouvre : le message du commit (Commit message, déjà proposé, du genre « Create 2026-10-14.md »), une description facultative, et le choix Commit directly to the v2 branch (enregistrer directement dans v2), à laisser coché. Cliquer le second bouton vert, Commit changes.
  5. Revenir. Fermer l'onglet GitHub, revenir à la page et cliquer Actualiser une minute plus tard : l'enregistrement apparaît, pour tout le monde.
Exemple sur notre canard

Les deux foot_top sortent de l'imprimante. Dans le registre des pièces, bouton « Enregistrer » de la ligne foot_top : exemplaire 1, état « imprimée » ; on recommence pour l'exemplaire 2. Deux petits fichiers arrivent dans biscalab/pieces/, chacun avec un commit à votre nom. Aucun PC à synchroniser.

Erreur classique. Fermer l'onglet après le premier bouton vert : sans le second Commit changes, rien n'est enregistré. Autre piège : si GitHub parle de « fork » ou affiche Propose changes (proposer des modifications), c'est que vous n'êtes pas connecté, ou pas encore collaborateur du dépôt du club. Ne pas continuer : se connecter, ou demander l'invitation à Jean-Marie.
Pourquoi un fichier par enregistrement. Chaque enregistrement est un fichier neuf, au nom daté. Deux membres qui enregistrent en même temps créent deux fichiers distincts : aucun ne peut écraser le travail de l'autre, et l'historique dit qui a enregistré quoi.

10. Suivre l'amont et respecter la licence

Récupérer les nouveautés d'Antoine : Sync fork

Le dépôt du club ne se met pas à jour seul quand Antoine publie une correction. Sur la page du dépôt du club, un bandeau le dit : « This branch is up to date with apirrone/Open_Duck_Mini:v2 » (à jour) ou « … commits behind » (en retard). En retard, on clique Sync fork (synchroniser), puis Update branch (mettre à jour la branche). Jean-Marie ou le référent outillage numérique le fait une fois par mois, puis chacun fait un Pull. Comme tout notre travail est dans biscalab/, cela ne crée jamais de conflit.

La licence Apache-2.0 en 4 obligations

Le projet d'origine est sous licence Apache-2.0 : on peut copier, modifier et redistribuer. Le dépôt du club est public : nous redistribuons, donc nous devons :

  1. fournir une copie de la licence (le fichier LICENSE reste dans le dépôt du club) ;
  2. conserver les mentions de droit d'auteur et d'attribution ;
  3. signaler de façon visible les fichiers modifiés (CHANGELOG.md, champ rev du registre des pièces) ;
  4. reprendre le fichier NOTICE s'il existe.

Aucune garantie n'est donnée, et aucun droit sur les marques (Disney, BDX). Notre biscalab/CREDITS.md rassemble ces mentions ; le cours 4 y revient.

Pourquoi c'est comme ça. Le canard existe parce que ses auteurs ont tout publié. Les citer est la contrepartie.

Exercice pratique au FabLab

Matériel : un PC par binôme avec GitHub Desktop, un compte GitHub par personne, invité comme collaborateur du dépôt du club. Le fichier d'essai biscalab/docs/essais.md est préparé par le référent outillage numérique, hors des dossiers du suivi que la page lit. Durée : environ 30 min.

  1. Créer son compte GitHub avec une appli d'authentification sur le téléphone, envoyer son nom d'utilisateur à Jean-Marie, puis accepter son invitation (e-mail « invited you to collaborate »).
  2. Se connecter dans GitHub Desktop : File → Options → Accounts → Sign in (Fichier → Options → Comptes → Se connecter).
  3. Télécharger le dépôt du club (page du dépôt → Code → Open with GitHub Desktop), en répondant « For my own purposes » si la question apparaît.
  4. Modifier biscalab/docs/essais.md avec le Bloc-notes : ajouter une ligne - date · prénom · mon premier commit, enregistrer.
  5. Commiter : Summary « Ajoute ma ligne au fichier d'essai », Commit to v2.
  6. Pousser et vérifier : Push origin, puis Repository → View on GitHub (voir sur GitHub). Ouvrir le fichier, trouver sa ligne, puis son nom dans l'historique.
  7. Provoquer un conflit à deux. A et B font un pull, puis modifient chacun différemment la même ligne « Prochaine séance : ». A commite et pousse. B commite et tente de pousser : refusé, le logiciel demande de récupérer d'abord.
  8. Résoudre. B fait Fetch origin puis Pull origin : le conflit s'annonce. B ouvre le fichier, choisit le texte avec A, supprime les marqueurs, enregistre, clique Continue merge, puis Push origin. A fait un pull.
  9. Enregistrer la séance depuis la page. Un binôme ouvre le Journal des séances, bouton « Nouvelle séance » : présents, et dans « Fait » une ligne « exercice Git du cours 1 ». Suivre la section 9 jusqu'au second Commit changes, puis Actualiser.

Résultat attendu : l'historique de biscalab/docs/essais.md montre le commit de chacun et un commit de fusion, sans texte perdu ; la séance du jour apparaît dans le journal de la page.

Auto-contrôle

Dans quel dépôt GitHub l'équipe travaille-t-elle, et faut-il en créer un à son nom ?

Dans le dépôt du club, JMTRIP/Open_Duck_Mini_Fablab, et nulle part ailleurs. Non : on demande à Jean-Marie d'être ajouté comme collaborateur, puis on le télécharge sur son PC avec GitHub Desktop.

Quels sont les trois étages, de haut en bas ?

Le dépôt d'Antoine (l'original, on n'y écrit pas), le dépôt du club (sur GitHub, partagé), la copie de travail sur chaque PC.

J'ai commité, mais mon collègue ne voit rien sur GitHub. Pourquoi ? Et si c'était une séance enregistrée depuis la page ?

Avec GitHub Desktop, il manque le Push origin : le commit est resté sur votre PC. Depuis la page, il manque sans doute le second Commit changes : le premier bouton vert ouvre seulement la fenêtre de confirmation. Recommencer depuis la page.

Pourquoi deux personnes ne doivent-elles pas modifier le même FCStd en même temps ?

C'est un fichier binaire : Git ne sait pas fusionner deux versions, l'une serait perdue. Règle : un éditeur par fichier, celui qui s'est assigné l'issue.

À quoi sert Sync fork, et pourquoi ne crée-t-il pas de conflit chez nous ?

Il récupère dans le dépôt du club les nouveautés du dépôt d'Antoine. Pas de conflit, car nous ne modifions jamais ses fichiers : notre travail est dans biscalab/.

Citez deux des quatre obligations de la licence Apache-2.0.

Fournir la licence ; conserver les mentions d'auteur ; signaler les fichiers modifiés ; reprendre le fichier NOTICE s'il existe.

À retenir

  • Un fichier garde son nom ; Git se souvient de ses versions, avec qui, quand et pourquoi.
  • Dépôt = le cahier ; commit = une photo datée avec légende ; branche = un chemin parallèle.
  • Trois étages : le dépôt d'Antoine (l'original), le dépôt du club JMTRIP/Open_Duck_Mini_Fablab (le seul où l'on travaille), votre PC (copie de travail). Seul biscalab/ est à nous.
  • Chez nous, la ligne principale s'appelle v2 : « Commit to v2 ». Pull en arrivant, Push en partant.
  • Le suivi (séances, pièces, achats…) s'enregistre depuis la page : GitHub s'ouvre pré-rempli, on clique deux fois Commit changes.
  • Une issue par tâche, avec un responsable, des étiquettes et un jalon.
  • STL, FCStd et 3MF ne se fusionnent pas : un éditeur par fichier.
  • Messages au verbe : « Ajoute… », « Corrige… ». Titres d'issues qui disent quoi faire.
  • Apache-2.0 : licence fournie, auteurs cités, modifications signalées, NOTICE repris.
